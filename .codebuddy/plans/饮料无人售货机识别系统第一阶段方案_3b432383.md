## 项目概述
仿照自动售货机的"基于 YOLO 的货架饮料识别与自助结算"系统：电脑摄像头对准货架，顾客"开门（开始识别）→ 取走饮料 → 关门（结束识别）"后，系统自动统计本次被拿走的饮料种类与数量，按内置单价生成结算单并模拟支付；货位出现空缺/低库存时后台向管理员提示补货；管理员后台提供近 7 天销量曲线等运营统计。

## 已确认需求决策
1. 顾客侧精简自助式：免注册登录，流程为"开门→取物→关门→自动出结算单→模拟支付"；仅管理员登录进入后台。
2. 技术栈：Python FastAPI + SQLite + Vue3 + ECharts，本地网页访问。
3. 摄像头形态：后端 OpenCV 接管电脑摄像头采集，前端实时预览并控制开始/结束识别。
4. 识别落地：默认"模拟识别事件"通道（确定性、可复现演示拿走 N 瓶饮料等场景）+ "ultralytics YOLOv8 预训练权重"真实摄像头通道（仅演示链路，不追求精度），两者可切换，统一切换与训练接口预留在方案中。
5. 补货判定：以货道库存为唯一事实源，成交扣库存，库存低于补货阈值即后台预警并支持手动补货登记；预留"视觉空位检测"接口，阶段一不深度实现。

## 技术选型
- 后端：Python 3.10+ / FastAPI + Uvicorn；OpenCV 负责摄像头采集与帧处理；ultralytics（YOLOv8）提供识别能力；SQLite（经 SQLAlchemy 或 sqlite3 均可，推荐 SQLAlchemy+SQLModel 简化迁移）单库存储；密码采用哈希（bcrypt/pbkdf2）存储。
- 前端：Vue3 + Vite + ECharts（近 7 日折线、品类占比饼图），axios 调用 API，原生 canvas/img 标签展示后端 MJPEG 视频流。
- 部署：FastAPI 托管静态前端产物与 API，本机浏览器访问 http://127.0.0.1:8000，局域网可访问；CORS 与静态资源同源部署，避免本地跨域问题。

## 总体架构

## 识别引擎与移除判定（阶段一）
- 抽象接口 DetectionProvider：`load(cfg)`、`detect(frame) -> List[Detection]`、`status()`；Detection 含 label/confidence/region/ts。
- SimulatedProvider（默认）：按演示脚本在会话内按时间产生"拿走 X 商品 N 件"事件与识别记录，用于稳定演示完整闭环。
- YoloCameraProvider：后端 OpenCV 逐帧取流（本地约 10-15fps 处理上限，预览流与检测线程分离），检测结果按"货架区域映射"写入识别日志；受限于无专用模型，仅演示链路，不做品牌级判定。
- 关门结算规则（事实源口径）：会话内事件按商品汇总净拿走量→按单价生成结算单→扣减对应货道库存→库存低于阈值生成补货预警→会话落库为已结算待支付，模拟支付后置为已支付。
- 训练接口预留（不训练但打通规范）：`models/`（权重产物目录）、`data/drinks/`（YOLO 格式 images+labels 与 data.yaml）、`configs/drinks.yaml`（类别名↔商品↔单价映射、置信度阈值）、`scripts/train.py`（封装 ultralytics train，阶段一只提供骨架与参数入口）；自定义权重就绪后仅替换模型路径与映射配置即可切换上层业务，无需改结算逻辑。

## 数据模型初稿
- product：id、名称、品牌、单价、单位。
- lane（货道/货位）：id、货架编号、关联 product、容量、当前库存 stock、补货阈值 threshold。
- session（会话/交易）：id、开始/结束时间、状态(open/closed/paid)、总额、支付时间。
- session_item：会话明细（product、数量、成交时单价、小计）。
- recognition_log：识别记录（会话、时间、帧号、provider、label、置信度、区域、是否计入成交）。
- restock_order：补货单（货道、商品、数量、操作管理员、时间）。
- alert（补货预警）：来源货道、类型(低库存/空位)、状态(待处理/已处理)。
- admin_user：管理员账号（用户名、密码哈希、角色）。

## API 与页面清单（写入 task.md）
- 顾客操作台 API：GET /api/camera/stream（MJPEG 预览）、POST /api/session/start、POST /api/session/stop（返回结算单）、POST /api/session/{id}/pay（模拟支付）、POST /api/demo/scenario（注入模拟拿走清单）。
- 管理员 API：登录鉴权；运营概览（总销售额/总订单数/识别准确率）；GET /api/stats/trend?days=7、/api/stats/category；会话列表与识别日志查询；库存列表与商品维护；补货登记；预警列表与处理。
- 模型/训练预留 API：GET /api/model/status、POST /api/model/switch（provider 切换）。
- 页面：顾客操作台页、管理员登录页、后台运营概览页、库存与补货管理页、预警与记录页（会话明细+识别日志）。

## 里程碑与验收（写入 task.md）
- M1 方案定稿（本轮 task.md）；M2 后端骨架：数据模型+模拟 Provider 跑通开门/关门/结算/扣库存/预警闭环；M3 前端：操作台实时预览+结算单+后台图表；M4 YOLO 摄像头通道接通与整体联调；后续阶段二再做数据标注、训练、自定义权重替换与视觉空位检测。
- 阶段一验收要点：模拟场景"拿走 2 瓶可乐+1 瓶冰红茶"关门后金额/库存/预警均正确；摄像头通道预览流畅且产生识别日志、不阻塞控制；后台近 7 日折线与品类占比随数据正确变化；全部管理接口需登录；初始化种子数据与对账无负库存。
- 风险与待办：识别准确率口径需真值来源（演示期可用注入/置信度口径并说明）；COCO 预训练无法细分饮料品牌，需后续标注训练解决；单会话并发限制需在文档中声明。
